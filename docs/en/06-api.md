# Management API

> English version of [`docs/06-api.md`](../06-api.md) (Turkish), which is the authoritative text; the two are updated together.

The interface is built on this API. To run it: `BOOTSTRAP_API_KEY=<key> make api-run` (127.0.0.1:58080). On the first run the root account and this key are created.

This document describes the Community API. The reseller, DID and invoice endpoints belong to the Enterprise edition and are documented there; the Enterprise binary also serves everything below.

## Rules

- People sign in with e-mail and password: `POST /v1/login` returns a session token (`tss_…`, valid for 12 hours), which is sent with `Authorization: Bearer` just like a key. Programs use API keys. In both cases permissions come from the role (`admin` or `readonly`).
- Authentication: `Authorization: Bearer <key>`. Every key belongs to an account and sees only that account's records. A record that belongs to someone else returns `404`. Community has a single account (the root).
- All amounts are **integer micro-units**: `1.000000` of a currency = `1000000`. Decimals are accepted only in the CSV tariff file.
- Balances cannot be changed directly; they change only through payments and calls.
- A client's balance is the amount available. A vendor's balance is what is owed to the vendor.
- Errors: `{"error": "..."}`; for the few rejections a program needs to tell apart there is also a fixed `code` (for now `two_step_required`, `own_two_step_off`; see "Two-step verification"). `400` invalid request, `401` key missing/invalid, `403` not permitted, `404` not found, `409` conflict, `422` validation error.
- Listing: `?limit=` (at most 1000), `?offset=` and equality filters by field name (e.g. `?status=active`). In addition: `?q=` searches in name/e-mail/tax number (clients, vendors, tariffs, plans); `rates.prefix`, `cdrs.dst` and `cdrs.src` match "starts with"; `?from=`/`?to=` (RFC 3339) for `cdrs`; `?validity=current|future|expired` for `rates`. The number of matching records is returned in the `X-Total-Count` header (except for `cdrs`; large tables are not counted).
- Keys start with `tsw_live_` and carry 32 letters/digits. `BOOTSTRAP_API_KEY` must also have this form (`tsw_live_` or `tsw_test_` + at least 16 letters/digits); the panel accepts no other form.

## Resources (GET list, GET single, POST, PATCH, DELETE)

| Path | Contents |
|---|---|
| `/v1/resellers` | Read-only; the root account |
| `/v1/clients` | Clients: billing type, credit limit, tariff, routing plan, limits |
| `/v1/client-trunks` | Client trunks: source addresses or username, tech prefix; `security` (`any`, `tls`, `cert`) and, for `cert`, `tls_cert_name`. `addresses` is the list of sources of a trunk identified by address (`auth_type: "ip"`): single addresses and networks (CIDR), IPv4 and IPv6, e.g. `["203.0.113.10", "198.51.100.0/24", "2001:db8:12::/48"]`. At least one item is required; the list is replaced as a whole on every write. The server stores and returns the list normalised: sorted, without duplicates, with the bits after the network length zeroed (`10.0.0.9/24` → `10.0.0.0/24`). An unreadable address, an empty list and a network wider than `/8` in IPv4 or `/16` in IPv6 give `422`; if the same address or network with the same tech prefix is on another enabled trunk, `409` (a disabled trunk holds no addresses; they are checked when it is enabled). A trunk identified by username does not use the list. The old single `ip` field has been removed (schema 0017 moves the existing address into the list). `max_contacts` (1–10, default 1): the number of addresses a trunk identified by username can have registered at the same time. Detailed settings (optional; `docs/08-cagri-arayuzu.md` (Turkish), "Bağlantı ve trunk ayarları", connection and trunk settings): `number_rules`: how the client writes numbers, a list of rules, e.g. `[{"strip": "00", "add": ""}, {"strip": "+", "add": ""}, {"strip": "0", "add": "90"}]`; the longest matching `strip` is applied to the number. `strip` is at most 8 digits (may start with `+`), `add` at most 8 digits; both cannot be empty, the same `strip` cannot appear twice, at most 20 rules; the list is replaced as a whole on every write and is returned with the longest `strip` first; anything else gives `422`. The old `number_strip` and `number_add` fields remain (schema 0025 moved the existing values into a one-rule list): a client that writes only them turns the list into a single rule (if both are empty the list is emptied); when reading, if the list has a single rule that rule is shown, otherwise they are empty. To empty a trunk with several rules through the old fields, write `number_rules: []` (two empty values do not count as a change). If both arrive in the same request, the list wins; `max_duration_sec` (0 or 5–7200); `max_calls`, `max_cps` (0 = none); `codecs` (the same names as in the connection's list); `transcode` (bool, default `false`: allows the audio to be transcoded when there is no common codec; `docs/08` (Turkish), "Kodek çevirisi", transcoding) |
| `/v1/vendors` | Vendors |
| `/v1/vendor-connections` | Vendor SIP connections: address, prefix add/strip, limits; for the `tls` transport, `tls_name` (the name the certificate must have been issued to; empty = the host). Detailed settings (all optional; their defaults are the old behaviour, meanings in `docs/08-cagri-arayuzu.md` (Turkish), "Bağlantı ve trunk ayarları", connection and trunk settings): `number_plus` (bool), `cli_strip_digits` (0–32), `cli_add_prefix` (digits, may start with `+`), `pai_mode` (`pass` / `remove` / `caller`), `ring_timeout_sec` (0 or 5–180), `max_duration_sec` (0 or 5–7200), `failover_mode` (`standard` / `always` / `never` / `custom`), `failover_codes` (codes between 300 and 699), `options_interval_sec` (0 or 10–3600), `codecs` (ordered list: `PCMA`, `PCMU`, `G729`, `G722`, `opus`, `GSM`, `iLBC`, `G723`, `AMR`, `AMR-WB`, `speex`), `transcode` (bool, default `false`: if there is no codec in common with the caller's trunk, the audio is transcoded and sent to this connection; `docs/08` (Turkish), "Kodek çevirisi", transcoding), `register` (bool, default `false`: the switch registers with the vendor using `auth_username` and the sign-in password; `docs/08` (Turkish), "Sağlayıcıya kayıt", registration with vendors), `register_expires_sec` (60–86400, default 3600: the registration period requested), `register_domain` (the domain of the registration address; letters, digits, `.` and `-`; empty = `host`). An out-of-range value gives `422`. Read-only: `auth_username` and `auth_set` (whether there is a password); both are written by the `sign-in` operation below, and the password itself (`auth_secret`) never appears in any response |
| `/v1/tariffs`, `/v1/rates` | Sell/buy tariffs and their rates. A tariff has a `timezone` (IANA name); a rate has an optional day and time window: `days`, `time_from`, `time_to` (`docs/08-cagri-arayuzu.md` (Turkish), "Güne ve saate göre fiyat ve rota", rates and routes by day and time). There is one rate per prefix, start and window |
| `/v1/holidays` | The account's public holidays (T-19, ADR-0044): `day` (`YYYY-MM-DD`; once per account), `counts_as` (the weekday the holiday counts as, Monday 1 … Sunday 7; default 7), `name`. Rate and route windows limited to a set of days count that date as this day; the date is read in the time zone of the tariff or plan. The list is sorted by date and filtered with `from`/`to` (RFC 3339). Generic CRUD: the audit log entry and the engine's snapshot refresh happen automatically |
| `/v1/routing-plans`, `/v1/routing-entries` | Routing plans and prefix → connection rows. A row has `priority` (lower first) and `weight` (0–1,000,000; the share between routes in the same step, 0 = failover only; an optional `days`, `time_from`, `time_to` window on the row, `timezone` on the plan; `docs/08-cagri-arayuzu.md` (Turkish), "Rota sırası ve ağırlıklı dağıtım", route order and weighted distribution) |
| `/v1/firewall-rules` | Firewall rules: `cidr` (address or network), `action` (`deny`, `allow`), `note`, `enabled`, `expires_at`. Only the rules of the account that operates the system are applied (`docs/08-cagri-arayuzu.md` (Turkish), "Güvenlik duvarı", firewall) |
| `/v1/report-schedules` | Scheduled reports: `name`, `period` (`daily`, `weekly`, `monthly`), `group_by` (the breakdowns of the summary report), `recipients` (comma-separated addresses), `timezone`, `send_hour` (0–23), `enabled`; `sent_through` is the end of the last period sent (read-only) |
| `/v1/exchange-rates` | Exchange rates: `currency` (three capital letters), `rate` (the value of 1 unit in the account's currency, in micro-units). Read-only: `source` (`manual` entered by hand, `ecb` follows the European Central Bank; this field cannot be written through the generic endpoints, `400`) and `published` (the publication day of a followed rate). A `PATCH` to a followed rate makes it manual (even if the value is the same). Details: `docs/08-cagri-arayuzu.md` (Turkish), "Para birimleri" (currencies) and "Kurların dış kaynaktan alınması" (exchange rates from an external source) |
| `/v1/cli-rules` | Caller ID (CLI) rules: `client_id` (empty = all clients), `number_source` (`from`, the default; `pai`: the number in `P-Asserted-Identity`), `prefix`, `action` (`block`, `allow`, `rewrite`, `anonymous`: reject a caller without a number with 433; the prefix and rewrite fields must be empty), for `rewrite` (only with `from`) `strip_digits` and `add_prefix`, `note`, `enabled`. There is one rule per number source and prefix in the same scope; `anonymous` can sit beside a rule with an empty prefix. Details: `docs/08-cagri-arayuzu.md` (Turkish), "Arayan numara kuralları" (CLI rules) |
| `/v1/bundles` | Minute bundles: `client_id`, `name`, `prefixes` (array of destination prefixes; an empty prefix means every number), `seconds` (billed seconds per calendar month), `enabled`. Filtered with `?client_id=`. Details: `docs/08-cagri-arayuzu.md` (Turkish), "Paket dakikalar" (minute bundles) |
| `/v1/cdrs` | Read-only list. `bundle_sec` is the seconds covered by a bundle, `bundle_id` the bundle (empty if the bundle was deleted). `trunk_id` is the caller's trunk; `dst_trunk_id` is the client trunk the call was delivered to (empty on a leg to a vendor and in records written before the field existed; `connection_id` and `vendor_id` are empty on that leg; the record keeps the ID even if the trunk is deleted later). It can also be used as a filter (`?dst_trunk_id=`). Records archived out of PostgreSQL (`CDR_KEEP_DAYS`) are still visible in the API when `CLICKHOUSE_URL` is set: `GET /v1/cdrs/{id}` serves a record it cannot find in PostgreSQL from ClickHouse; when the list reaches back before the archive horizon (`cdr_archive.horizon`), it serves the part after the horizon from PostgreSQL and the part before it from ClickHouse, with the same order and paging. The row format is the same; only extension columns that ClickHouse does not have (Enterprise: `did_id`, invoice IDs) are `null` in an archived row, and a filter on such a column returns no rows from the archive. If ClickHouse cannot be read, the records in PostgreSQL are returned |
| `/v1/audit-log` | Audit log; read-only, newest first (see "Audit log" below) |

## OpenAPI description

`GET /v1/openapi.json` (authenticated) returns the OpenAPI 3.0 description of the API. The description is not written by hand: the running server generates it from its registered paths and its resource table, reading the field types from the database. It therefore cannot drift from the code, and the resources and endpoints that other editions add are included automatically. The generic resource endpoints (list, single, create, update, delete) are fully described with their filters and schemas. The custom operations (payments, CSV upload, simulator, reports…) are described too, with summary, query parameters, request body and the body of every response code (T-21): the schemas are generated by reflection from the Go types the handler reads and writes. Every rejection has the same form (`Error`: `{"error": "...", "code"?}`, `4XX`).

```bash
curl -H "Authorization: Bearer $KEY" http://127.0.0.1:58080/v1/openapi.json > openapi.json
```

### Describing a new endpoint

An endpoint is registered with `s.Handle` or `s.HandlePublic` (one registered directly with `s.mux` is not in the description), and its registration line says what it takes and what it returns; the options do not change how it runs, they only feed the description (`pkg/api/schema.go`):

```go
s.Handle("POST /v1/firewall/unban", true, s.firewallUnban,
	api.Summary("Lift such a ban before its time is up."),
	api.Takes(unbanRequest{}), api.ReturnsNothing())
```

| Option | Meaning |
|---|---|
| `Summary(text)` | One-line summary (required) |
| `Takes(v)` | JSON request body; `v` is the zero value of the type the handler decodes |
| `TakesText(type, description)` | Non-JSON request body (e.g. `text/csv`) |
| `TakesNothing()` | `POST`/`PUT`/`PATCH` without a body |
| `Returns(code, v...)` | JSON response; several values mean "one of these" (`oneOf`); an endpoint that answers with several codes writes it once per code |
| `ReturnsNothing()` | 204, no body |
| `ReturnsText(type, description)` | Non-JSON response (CSV, pcap) |
| `ReturnsRow(code, resource)` / `ReturnsRows(resource)` | A row or a list of a resource (with the resource's schema) |
| `ReturnsTableRows(table, extra)` | Rows with all the columns of a table plus the fields of the `extra` type |
| `Query(name, v, required, description)` | Query parameter |

Schema rules derived from the type: the name in the `json` tag; in a response, a field without `omitempty`/`omitzero` is always present (`required`); in a request no field counts as required, and a missing field the handler rejects is marked with the `openapi:"required"` tag; a pointer is `nullable`; `int64` (money included) is `integer`/`int64`; `time.Time` is `date-time`; `json.RawMessage` is any value, but a field that passes a resource's row through as it is takes that resource's schema with `openapi:"ref:<resource>"`; `json.Number` is `number`; the fields of an embedded struct join the outer struct. Named structs are shared in responses under `components/schemas` by type name (first letter capitalised); if the same name exists in two packages, the package name is prefixed. Request bodies are written in place, without components.

Checks: `TestEveryOperationDescribed` in `go test ./pkg/api` requires a summary, a response and (for `POST`/`PUT`/`PATCH`) a request description on every non-generic endpoint; a new endpoint without a description fails the test. `make test-api` compares the real request and response of every custom operation (rejections included) with the schema in the description: a field not in the description, a field the description requires that does not arrive, or a wrong type fails the test. The types of the endpoints that pass the engine's response through (`engineviews.go`) are compared with the engine's own in `TestEngineViewsMatch`. `make test-openapi` generates the document against the test database and lints it with Redocly (`redocly.yaml`: all recommended rules at error level; no rule turned off).

Enterprise and other extensions use the same options in their own registrations; an endpoint registered without options appears in the description with only its path and "200 OK".

## Operations

| Request | Description |
|---|---|
| `GET /v1/me` | The caller's account record |
| `GET /v1/session` | `{edition, version, key: {id, name, role}, account}`; `version` is the release the API runs (`v0.1.0`; `dev…` for a development build; ADR-0051) and is not given on any open endpoint; in a user session also `user: {id, name, email, role, two_step, two_step_setup_required}`. The panel opens the session with this; if `two_step_setup_required` is true it shows only the setup screen. `account.require_two_step` is the account's setting |
| `POST /v1/login` | `{"email", "password"}` → `{"token", "expires_at"}`. A failed sign-in gives `401`; after five failed attempts in a row the account is locked for 15 minutes (`429`). If the user has two-step verification on, `{"two_step": true, "challenge", "expires_at"}` is returned instead of a token: `challenge` (`tsc_…`, valid for 5 minutes) is not a session, only the right to present the code. If the account has made two-step verification mandatory and the user has not set it up, the response also has `"two_step_setup_required": true`: the session is open to the setup only |
| `POST /v1/login/verify` | The second step of sign-in: `{"challenge", "code"}` → `{"token", "expires_at"}`. `code` is the 6-digit code from the app or a recovery code. A wrong code gives `401` and counts towards the lock like a wrong password; an expired or used `challenge` gives `410`; a locked account `429` |
| `POST /v1/logout` | Ends the session |
| `POST /v1/password/forgot` | `{"email"}`; if the address belongs to a user, a single-use reset link valid for 30 minutes is sent by e-mail. The response is the same whether the address is registered or not (`204`); no more than one link is sent per minute. If e-mail is off, `503` |
| `POST /v1/password/reset` | `{"token", "password"}`; an invalid or used link gives `410`. The new password signs the user out of their sessions and lifts the lock |
| `POST /v1/me/password` | `{"current", "new"}`; the user's other sessions are closed |
| `GET /v1/me/two-step` | Two-step verification of the user in the session → `{"enabled", "recovery_codes_left"}`. The `me/two-step` endpoints work only with a user session; with an API key, `400` |
| `POST /v1/me/two-step/setup` | Starts the setup → `{"secret", "uri"}` (`secret` in base32, `uri` the `otpauth://` address that apps read from the QR code). Nothing is turned on until a code is confirmed; asking again changes the pending secret. If it is already on, `409` |
| `POST /v1/me/two-step/confirm` | `{"code"}`; if correct, two-step verification is turned on → `{"recovery_codes": [10 codes]}`. The codes appear only in this response. A wrong code gives `422` |
| `POST /v1/me/two-step/recovery-codes` | `{"code"}` (the code from the app; a recovery code is not accepted) → 10 new recovery codes; the old ones become invalid. A wrong code gives `403` and counts towards the lock |
| `POST /v1/me/two-step/disable` | `{"password", "code"}` (`code` is an app code or a recovery code); turns two-step verification off and deletes the secret and the recovery codes. A wrong password or code gives `403` and counts towards the lock |
| `GET /v1/account/two-step` | Whether the account requires two-step verification (T-23, ADR-0045) → `{"required", "users_without"}`; `users_without`: the number of the account's active users who have not set up the second step. Read-only roles can read it too |
| `PUT /v1/account/two-step` | `{"required": true}` or `{"required": false}` → the same response. Requires admin. A person turning it on from a session must have their own second step on (otherwise `409`, `code: "own_two_step_off"`); an API key turns it on and off unconditionally. Written to the audit log on the `account` resource as `require_two_step_on` / `require_two_step_off`; a call that does not change the value leaves no entry |
| `POST /v1/users/{id}/two-step/reset` | An admin removes another user's two-step verification (lost phone); the user signs in with the password only and can set it up again. A person cannot remove their own this way (`422`) |
| `GET /v1/users` | Users (the password hash is not returned); `locked` shows a locked account, `two_step` one with two-step verification on |
| `POST /v1/users` | `{"email", "name", "role", "password"}`; the password is at least 10 characters, the e-mail is unique (`409`) |
| `PATCH /v1/users/{id}` | `name`, `email`, `role`, `status` (`active`/`disabled`), `password`, `unlock`. A new password or disabling closes the user's sessions; a person cannot change their own role or status |
| `DELETE /v1/users/{id}` | A person cannot delete themselves |
| `GET /v1/api-keys` | Keys (neither the value nor the hash is returned); `current` marks the caller's key |
| `POST /v1/api-keys` | New key; the key appears only in this response |
| `DELETE /v1/api-keys/{id}` | Revokes the key; the key in use cannot be revoked (`409`) |
| `POST /v1/tariffs/{id}/rates/import` | CSV tariff upload. Header: `prefix,price_per_min[,connect_fee,initial_sec,increment_sec,grace_sec,blocked,days,time_from,time_to]` (the short forms `price`, `initial`, `increment`, `grace` are also accepted). Optional window (T-19): `days` is the API's set of days (1–127; empty = every day), `time_from` and `time_to` are `HH:MM` in the tariff's time zone (both together and different; `24:00` at the end is midnight); the same prefix can be on several rows with different windows, the same prefix and window cannot appear twice. A file without window columns is loaded as before. Window errors: `days_invalid`, `time_invalid`, `time_pair`. Parameters: `effective_from`, `mode=close` (default; moves the end of the current rates on the same prefix, windowed ones included, to this date) or `mode=keep` (rejects prefixes that have a current rate), `dry_run=1` (validates only). Invalid rows are skipped; the response carries `read`, `valid`, `invalid`, `errors[{line, prefix, value, code}]`, `closed`, `new_prefixes`, `rates`. If there is no valid row at all, `422` |
| `GET /v1/exchange-rate-feed` | Exchange rates from an external source (T-20) → `{"enabled", "source", "published", "fetched_at", "failed_at", "error", "missing", "currencies"}`. `enabled` is on with `FX_SOURCE=ecb`; `published` is the day of the last table fetched, `fetched_at` the last successful fetch, `error` the reason if the last attempt failed (contains no address; cleared on a successful fetch), `missing` the rates that follow the source but are not in the table (`"JPY/USD"`: currency/account currency; their last values remain), `currencies` the currencies published (euro included). Read-only roles can read it too |
| `POST /v1/exchange-rate-feed/fetch` | Fetches the table now and rewrites the rates that follow the source → `{"published", "changed", "missing"}`. If it is off, `409`; if another process is fetching at that moment, `409`; if the source cannot be reached or the file cannot be read, `502` (the last rates remain, and the error shows in the status). Requires admin; written to the audit log as `fetch`, and every rate that changed is also written as `update` on behalf of "system" |
| `POST /v1/exchange-rate-feed/follow` | `{"currency"}`: in the caller's account, makes the rate of that currency follow the source; the rate is added if it does not exist, converted if it was manual, and its value is computed at once from the last table fetched → the rate's row. If it is off or no table has been fetched yet, `409`; if the code is not three capital letters or cannot be computed from the table, `422`. To make it manual, use the generic `PATCH /v1/exchange-rates/{id}` |
| `POST /v1/payments` | `{party_type, party_id, amount, kind, reference, note}`; `kind`: payment, adjustment, refund |
| `GET /v1/ledger?party_type=&party_id=` | Transactions |
| `POST /v1/cdrs` | Rates raw call records (a record can carry `src_ip`, `pdd_ms` and `dst_trunk_id`); idempotent on `(call_id, leg)`. An unknown field returns `400`; an extension declares its own field with `AllowCDRField`, and the field reaches the `OnCDRStored` hook in `CDR.Extra` (the rater goes through the same path) |
| `POST /v1/route/simulate` | `{src_ip, dst, src, asserted, at}`; `at` (RFC 3339) is the moment the call would start, now if omitted; `src` (caller ID) and `asserted` (the number in `P-Asserted-Identity`) are optional; if neither is given, CLI rules are not applied (if one is given, the other counts as having no number); if given and a rule changes the number, the response contains `caller`; returns the routing decision and the route order; every route has `step` and `share_pct` (its share of first attempts within its step). If the call would be covered by a bundle, `bundle_id` and `bundle_free_sec` (seconds left in the bundle) are returned |
| `POST /v1/report-schedules/{id}/send` | Queues the scheduled report at once for its last completed period → `{"period_start", "period_end", "recipients"}`. If there is no mail server, `409` |
| `GET /v1/firewall/bans`, `POST /v1/firewall/unban` | Addresses blocked automatically because of flooding (from the engine) and lifting a block (`{"ip"}`); only the account that operates the system |
| `GET /v1/trace?call_id=` | The stored SIP messages of a call, with all route attempts, in the order they passed → `{call_id, messages[{at, direction, transport, src_ip, src_port, dst_ip, dst_port, line, raw}], truncated}`. `at` is UTC with microseconds; `direction` is `in` (received by the SIP core) or `out`; `line` is the first line of the message; `raw` the raw text (password digest as `***`). At most 2,000 messages (`truncated`). A call without a trace returns an empty list. If the call's record does not belong to one of the caller's clients, `404`; a call without a record (still in progress) is visible only to an account that sees all clients. If ClickHouse is not configured or cannot be read, `503`. Details: `docs/en/10-monitoring.md`, "Call trace" |
| `GET /v1/trace/pcap?call_id=` | The same messages as a capture file that Wireshark opens (`application/vnd.tcpdump.pcap`). The headers are generated and TLS messages appear decrypted: this is not a capture taken from the wire. If there is no trace, `404` |
| `GET /v1/system` | The state of the server (only the account that operates the system): `machine` (CPU in per mille, load, memory, network; samples of the last ten minutes; disks) and `services` (whether each service answers, and in how many milliseconds). Outside Linux `machine.supported` is false and only the disks are filled in |
| `GET /v1/reports/summary?group_by=&from=&to=` | `group_by`: client, vendor, prefix, day. The rows count attempts (call legs). Revenue, cost and margin are in the account's currency. Quality fields: `asr_pct`, `acd_sec`, `ner_pct` (the share of attempts not ended by the network; the same definition as in the live monitor: failures other than 402, 403, 404, 480, 484, 486, 487 and 6xx are network failures), `pdd_ms` (average post-dial delay of attempts that reported progress), and the raw numbers `failed_network`, `pdd_samples`, `pdd_sum_ms` for adding up totals |
| `PUT /v1/vendor-connections/{id}/sign-in` | `{"username", "password"}`: the name and password the switch uses to sign in to the vendor (when the vendor challenges with 401/407). The password is stored encrypted with `SECRET_KEY` and cannot be read back from any endpoint; the response is `{"auth_username", "auth_set": true}`. Requires admin; written to the audit log as `sign_in_set`, with the username only. An empty value or one longer than 128 characters gives `422` |
| `DELETE /v1/vendor-connections/{id}/sign-in` | Removes the sign-in name and password (`sign_in_cleared`) |
| `POST /v1/vendor-connections/{id}/test` | Tests the connection: the engine sends a single SIP `OPTIONS` to the vendor now. Response `{"outcome", "sip_code", "sip_reason", "ms", "detail"}`; `outcome`: `answered` (with its code and time), `no_answer`, `unresolved` (host name not found), `refused` (nobody listening), `certificate` (certificate not accepted), `failed`. Changes nothing and is not written to the audit log. Requires admin; if the engine cannot be reached, `503` |
| `GET /v1/vendor-connections/health?vendor_id=` | The state of the connections the engine pings (enabled, with `options_interval_sec` set) and of the switch's registrations with vendors: `{"connections": {"<id>": {"state": "up" / "down" / "unknown", "since", "checked_at", "last": {…}}}, "registrations": {"<id>": {"state": "registered" / "pending" / "failing" / "unknown", "reason", "since", "checked_at", "expires"}}}` (the `reason` values are in `docs/08-cagri-arayuzu.md` (Turkish), "Sağlayıcıya kayıt", registration with vendors). A connection that is not pinged or does not register is not in the relevant list; only the connections the caller can see are returned |
| `POST /v1/client-trunks/{id}/password` | Gives a trunk identified by username a new random password → `{"username", "password", "realm"}`. The password appears only in this response; the old one becomes invalid at once. For a trunk identified by IP, `409` |
| `GET /v1/registrations?client_id=` | The current registrations (REGISTER) of the client's trunks → `{"registrations": [{trunk_id, contact, src_ip, src_port, transport, nat, since, until, user_agent}]}`. `contact` is the address the device reported, `src_ip`/`src_port` where the registration actually came from, and `nat` says the device is reached at that address; `since` is the first registration, `until` the end of validity. The engine holds the registrations; if the engine is not configured or cannot be reached, `503`. `client_id` is required (`400`) |
| `GET /v1/client-trunks/{id}/registrations` | The registrations of a single trunk, in the same form. For a trunk identified by address the list is empty |
| `DELETE /v1/client-trunks/{id}/registrations` | Deletes the trunk's registrations; with `?contact=`, only that address. The remaining registrations are returned. If there is no such registration, `404`. The trunk is not blocked; the device can register again. Requires admin; written to the audit log as the `unregister` operation, with the addresses deleted |
| `GET /v1/clients/{id}/bundles` | The client's bundles; in addition to the bundle's fields each row has `period` (the current period, `YYYY-MM`, in the tariff's time zone) and `used_sec` (the seconds taken from the bundle in this period). Seconds held by calls in progress are not included |
| `GET /v1/balance-alerts?state=open\|cleared&client_id=` | Low balance alerts (read-only). The threshold is the client's `low_balance` field (micro-units; `null` = no alert). Every 10 seconds the API process looks at all clients: if the balance has fallen to or below the threshold it opens an alert, and if it has risen above it or the threshold has been removed it closes it |
| `GET /v1/audit-log/export?…` | The same filters as the audit log list (apart from `limit`/`offset`); all matching entries, newest first, as CSV (T-23). Columns: `id, at, actor_type, actor_id, actor_name, ip, resource, row_id, action, label, changes, detail`; `changes` and `detail` are JSON text, and secrets are `"***"` as in the list. Server-side streaming: rows go out as they are read from the database (sent every 1,000 rows), not collected; there is no limit on the number of entries (the retention period limits it). Names and labels that start like a formula (`=`, `+`, `-`, `@`) get a `'` prefix so that spreadsheet programs do not treat them as formulas. Anyone who can read the list (read-only roles included) can download it |
| `GET /v1/cdrs/export?…` | The same filters as the CDR list; all matching records as CSV (names filled in, amounts as decimals). More than 200,000 records returns 422. The last columns are `bundle_sec` and `dst_trunk` (the name of the client trunk delivered to; empty on a leg to a vendor). Archived records come from ClickHouse at the end of the file by the same rule as the list, in the same format; the limit applies to the total of the two sources |
| `GET /v1/live` | Traffic of the last 60 seconds: `live` (route-engine's response; the fields are in `docs/08-cagri-arayuzu.md` (Turkish)), `clients` and `connections` (ID → name) |
| `GET /v1/live/calls?client_id=&offset=&limit=` | Calls in progress: `total`, `calls`, names |
| `POST /v1/live/calls/hangup` | `{"call_id": …}`; hangs up an answered call (admin key) |

The live endpoints read their data from route-engine; its address is given to the API with `ENGINE_URL` and the secret the engine expects with `ENGINE_TOKEN`. If the address is not given or the engine does not accept the API's secret, 503 is returned (the secret appears in no response). Because live traffic is not split by account, only an account that sees all clients can access it; others get 403.

For a complete example flow: `pkg/api/api_test.go`.

## Audit log

Every change made through the management API is written to the `audit_log` table inside the database transaction that makes the change: there is no change without an entry and no entry without a change. Reading: `GET /v1/audit-log` (and `/{id}`); read-only roles can read it too.

| Field | Meaning |
|---|---|
| `at` | Time (UTC) |
| `reseller_id` | The account of whoever made the change. Visibility follows it: each account sees only what its own users and keys did (in Enterprise a parent account also sees its sub-accounts') |
| `actor_type`, `actor_id`, `actor_name` | Who: `user` (the e-mail instead of a name), `key` (the key's name) or `system`. The name is the value at the time of the entry; it remains even if the user or key is deleted later |
| `ip` | The address the request came from. If the API is behind a reverse proxy, set `TRUST_PROXY=1`; otherwise the proxy's address is written |
| `resource`, `row_id`, `label` | What: the resource name in the API path (`clients`, `rates`, `users`…), the row's ID and the name people give it (name, e-mail, prefix, address) |
| `action` | `create`, `update`, `delete` or a named operation (below) |
| `changes` | `{"old", "new"}` per field. On an update only the fields that changed; on a create only `new`, on a delete only `old` (the last state of the deleted row). An update that changes nothing leaves no entry |
| `detail` | Details of a named operation (amount, reference, reason…) |

Filters: `from`, `to` (RFC 3339), `actor_type`, `actor_id`, `resource`, `action`, `row_id`, `q` (searches in names, labels, addresses and changed values), `limit`, `offset`; the number of matching entries is in the `X-Total-Count` header.

Export: `GET /v1/audit-log/export` streams all entries matching the same filters as CSV (see the endpoint table above). Since secrets never enter the table, they are not in the file either; the file carries exactly the values of the list. Export to syslog/SIEM is a separate task (T-47).

Named operations: `payment` / `adjustment` / `refund` (balance; resource `clients` or `vendors`), `rates_import` (resource `tariffs`; a dry-run upload leaves no entry), `password_issued` (a trunk password was generated; the password itself is not written), `hangup` (resource `live-calls`, label the Call-ID), `unban` (resource `firewall`), `send` (a scheduled report was sent by hand), `submit` (`POST /v1/cdrs`), and for users `login`, `login_failed` (`detail.reason`: `password`, `code`, `disabled`; `detail.locked`: whether this attempt locked the account), `password_changed`, `password_reset_requested`, `password_reset`, `two_step_on`, `two_step_off`, `two_step_reset`, `recovery_codes_renewed` (on sign-in, `detail.two_step_setup_required`: the account has made the second step mandatory and the user has not set it up), and for the account `require_two_step_on` / `require_two_step_off` (resource `account`). Creating and revoking an API key are written on the `api-keys` resource as `create` / `delete`.

Rules:

- **Secrets never enter the log.** Passwords and their hashes, API key values, session tokens, the engine's secret, two-step verification secrets and codes are never written. This is not a list but a rule of the single function that writes: the columns a resource hides (`Resource.Hide`) and every field whose name looks like a secret (`pass`, `secret`, `token`, `hash`, `ha1`, `otp`, `key`…) are written as `"***"`; you can see that the field changed, not its value.
- **The log cannot be changed.** There is no endpoint in the API that writes, corrects or deletes it (`405`).
- **Retention:** `AUDIT_RETENTION_DAYS` (default 365 days; `0` = keep forever). Once an hour the API process deletes expired entries.
- **No writing endpoint can stay out of the log.** Generic create/update/delete, including resources an extension adds, is logged automatically. When a writing endpoint that does not write its own entry (`Handle(…, true, …)`) finishes successfully, a plain entry derived from the endpoint's name is written (resource = the first segment of the path, action = the last). Extensions call `Server.Audit` for a detailed entry; a call that changes nothing (a preview) says so with `AuditNothing`.
- A sign-in attempt with an unknown e-mail address is not logged: there is no account it would belong to, and an unauthenticated party could fill the log. Failed attempts on a known user are logged and are bounded by the lock.
- The entries of the two operations carried out in the engine (`hangup`, `unban`) and of `submit` are written after the operation finishes; there is no shared database transaction for them.

## Two-step verification

Panel users can use a time-based one-time code (TOTP, RFC 6238: SHA-1, 6 digits, 30 seconds) in addition to the password when signing in; it works with common authenticator apps. To allow for clock drift, the codes of the previous and the next step are also accepted. A code is valid once: the accepted step is stored, and it and earlier ones are not accepted again (the code that confirms the setup included). Recovery codes (10, each usable once) stand in for the code. Wrong codes go to the same counter as wrong passwords (five failures, 15-minute lock). API keys are not affected.

If `SECRET_KEY` (64 hexadecimal digits) is set, the secret is stored in the database encrypted with AES-256-GCM, bound to the user's ID; if it is not set, the secret is stored in clear and the API writes this to the log at start-up. If the key is set later, old rows can still be read; if the key is lost, the encrypted secrets cannot be read and an admin has to reset those users' two-step verification. Only the hash of recovery codes is stored. Generating codes and storing the secret live in the `pkg/totp` package; the Enterprise client portal uses the same package.

A password reset (by e-mail or with a new password set by an admin) does not remove two-step verification.

**Making it mandatory (T-23, ADR-0045).** The account's admin can make the second step mandatory for all panel users of the account with `PUT /v1/account/two-step` (`resellers.require_two_step`, off by default). While it is on, a user who has not set up the second step signs in with the password and gets an ordinary session, but the session reaches only the endpoints `GET /v1/session`, `GET /v1/me`, `GET /v1/me/two-step`, `POST /v1/me/two-step/setup`, `POST /v1/me/two-step/confirm` and `POST /v1/logout`; every other endpoint (extensions' included) returns `403` and `{"error", "code": "two_step_required"}`. The restriction is read on every request: when the setting is turned on, open sessions are restricted on their next request, and once the setup is confirmed the same session is opened at once; a user reset by an admin while the setting is on also goes back to the setup. API keys are not affected. A person who turns the setting on from a session must have their own second step on (`409`, `own_two_step_off`); nobody gets locked out, because the setup is open to everyone who is restricted. In Enterprise each reseller account has its own setting; the client portal is outside this rule.

## E-mail

The API process sends e-mail in one of two ways; both use the same queue:

| Environment variable | Meaning |
|---|---|
| `RESEND_API_KEY` | Resend API key; sending is done through Resend's HTTP API |
| `SMTP_URL` | SMTP server: `smtp://user:password@host:587` (TLS is started if the server offers it) or `smtps://…:465` |
| `MAIL_FROM` | Sender address, e.g. `Telrics <no-reply@example.com>`; with Resend it must belong to a verified domain |
| `PANEL_URL` | The panel's address; links in e-mails are built with it |

`RESEND_API_KEY` and `SMTP_URL` cannot be given together; if neither is given, e-mail is off and nothing is written to the queue.

A message is written to the `mail_outbox` table together with the database transaction that caused it, and is sent by the API process. A message that cannot be sent is retried eight times with a doubling interval (1 min, 2 min, 4 min…); the last error stays in the `last_error` column.

Messages sent: the password reset link and the low balance alert (to the client's e-mail address, once when the alert opens). Messages are plain text and in Turkish.

In the lab, messages do not leave the machine: the mail catcher (Mailpit) holds them all, readable at http://127.0.0.1:58025. `make test-mail` tries the flow end to end.
